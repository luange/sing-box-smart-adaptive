# v1.14.0-beta.14-smart-tcv2.21-udp-profile

Base: official sing-box `v1.14.0-beta.14`.

## User-visible changes

- Preserve the eBPF original-destination mapping for the full lifetime of a
  UDP flow. TCP still consumes its mapping exactly once after accept.
- Bound shared redirect and direct-verdict state with LRU maps so expired
  epochs cannot permanently occupy capacity.
- Feed real DNS, QUIC and STUN request/response blackholes into both ordinary
  `type: smart` and AdaptivePool node health.
- Submit at most one no-response failure per transactional UDP flow.
- Do not penalize one-way UDP or an idle timeout after any response.
- Reuse existing Smart reliability, breaker, affinity and switch auditing;
  no parallel health database or scheduler is introduced.

## Operational effect

- A node that accepts a UDP socket but blackholes QUIC is progressively
  downgraded and removed from subsequent Smart selections.
- Ordinary YouTube TCP fallback remains available when provider nodes do not
  support HTTP/3.
- DNS and explicit direct UDP retain the eBPF/DNS-multiplexer fast paths and
  do not become persistent Clash connection rows.

## Validation

- Linux eBPF generation/check, targeted tests, race detector and vet passed.
- VM117: Google 204 and YouTube HTTP 200; repeated HTTP/3 blackholes changed
  the selected Smart candidate; RSS remained about 57--59 MiB.
- VM115 canary: Google 204 and YouTube HTTP 200 through the actual HK PBR
  ingress; no panic, fatal error, queue drop or original-destination loss.

## Known boundary

HTTP/3 availability remains provider-node dependent. Smart can avoid observed
blackholes but cannot add UDP support to a proxy node that does not provide it.
Seven-day production stability is not claimed by this release.
